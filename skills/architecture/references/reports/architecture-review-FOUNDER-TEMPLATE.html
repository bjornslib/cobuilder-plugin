Any logged-in user can see another customer's orders

What We Found: Your orders API checks "is this person logged in?" but never asks "does this order belong to this person?" The database query asks for an order by its number, not by its owner.

Impact If Not Fixed: Under GDPR and most B2B contracts, exposing one customer's data to another is a reportable breach. If discovered during investor due diligence, this is a deal-breaker. If discovered by a customer first, it becomes a reputational crisis.

A user who guesses or sees another order number in a notification can open that order and view the full contents -- customer name, email, address, and purchase history. This is a data breach waiting to happen.

Order numbers are guessable -- anyone can scrape your entire customer base

What We Found: Your API returns simple sequential numbers as order IDs (1, 2, 3, 4...). An attacker can write a script that tries number 1, then 2, then 3, and collect every order in your system.

Impact If Not Fixed: This is how data breaches start. It also violates the spirit of GDPR's data minimisation principle. Once a single order is exposed via tenant isolation bugs, sequential IDs make the rest trivial to harvest.

Replace exposed numbers with long random IDs in URLs. Inside the database you can still use simple numbers; just never send them to the frontend.

Your most important words (Bank, Entity) mean different things in different parts of the code

What We Found: "Bank" is used 254 times to mean three different things: a customer-facing account, a configuration namespace, and a database storage container. "Entity" is used 373 times to mean both a business concept (a person or organisation) and a database row. Every package depends on every other package through one oversized "engine" file. There is no shared dictionary of terms, so when a developer joins, they must learn the code to understand the words.

Impact If Not Fixed: Ambiguous language is the leading cause of cross-team miscommunication and bugs at scale. When "Bank" means three things, a change to one quietly breaks another. Decomposing the system into services becomes impossible without first resolving these collisions.

Produce a glossary first: one list defining every core term (Bank, Entity, User, Account) and which team owns it. Then rename database-facing occurrences to Record or Row so the business words stay clean.

Recommended before hiring or decomposing services

Your orders list will crash when a customer has more than a few hundred orders

What We Found: When a user opens "My Orders," your app asks the database for every order that user has ever placed, then sends them all at once. For a power user with 10,000 orders, this is a 400MB download that times out.

Impact If Not Fixed: This is what causes the "spinning wheel" user experience and 500 errors at scale. It also makes your hosting bill spike.

Show orders 25 at a time with a "Load more" button. This is standard practice.
