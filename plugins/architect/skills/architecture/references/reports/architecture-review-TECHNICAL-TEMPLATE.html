Security Findings

Two verified security issues. Both require remediation before production exposure.

P0 SEC-01 — Missing authorization guard in /api/orders.py:47 → Founder view

Technical description: The GET /api/orders/ endpoint retrieves an order by primary key without verifying ownership. Any authenticated user can pass any order_id and receive the full record, including customer name, email, and line items.

Root cause: The SQL query at line 47 uses WHERE id = ? but omits AND user_id = ?. No service-layer check follows.

/src/api/orders.py:47
47 order = db.execute("SELECT * FROM orders WHERE id = ?", (order_id,))
48 return OrderSchema().dump(order)

Recommended fix: Add AND user_id = current_user.id to the WHERE clause. Add a test that proves an authenticated user cannot access another user's order. See founder report for pre-built AI prompt.

P1 SEC-02 — Internal object IDs exposed in API responses → Founder view

Technical description: API responses expose sequential integer primary keys for orders, users, and products. This enables ID enumeration attacks — an attacker can increment IDs to scrape all records.

Evidence: OrderSchema at /src/schemas/order.py:12 includes id field with no transformation. No UUID obfuscation layer exists.

Fix: Replace exposed primary keys with opaque UUIDs or hash IDs before serialization. Update frontend consumers to use the new key format.

Architecture Findings

One structural issue affecting long-term velocity and separation of concerns.

P1 ARCH-01 — Presentation logic mixed with business rules in runner.py → Founder view

Technical description: runner.py (2,421 lines, 74 methods) handles HTTP request parsing, database access, business rule validation, and response formatting in a single file. This violates Single Responsibility Principle and Hexagonal Architecture boundary rules.

Fix: Extract controllers (HTTP), use cases (business rules), and presenters (formatting) into separate modules. Decompose runner.py over three phases — dot_writer, handler modules, then broker extraction. See runner-decomposition-2026-05-26.html for the full plan.

P2 ARCH-02 — Core concepts conflated across domain packages; DDD glossary missing → Founder view

Technical description: Bounded-context subdirectories exist (consolidation/, search/, retain/) but share a database schema and a central hub class that imports from 8+ subdomains while being imported back by 14. The term "Bank" (254 cross-module refs) conflates aggregate root, configuration namespace, and storage container. "Entity" (373 refs) conflates domain identity (Person) with database row (DBEntity). No anti-corruption layers or domain events exist between subdomains.

Evidence: memory_engine.py at hindsight/engine/memory_engine.py:1 imports from consolidation/, search/, retain/, storage/, providers/, directives/, mental_models/, reflect/. In return, 14 sub-packages import MemoryEngine back. search/ reaches into retain/storage_model.py directly.

Fix: Before decomposing memory_engine.py, produce a DDD glossary and context map: define Bank as aggregate root, BankConfig as value object, BankSchema as infrastructure. Rename overloaded infrastructure-facing "Entity" to Record or Row. Then extract anti-corruption layers between subdomains.

Scaling Findings

P2 SCAL-01 — API endpoints return unbounded result sets → Founder view

Technical description: GET /api/orders at /src/api/orders.py:62 returns all orders for a user without pagination or cursor limits. Response payloads grow unbounded — tested with a synthetic user having 50,000 orders, response exceeded 400MB and timed out at Heroku 30s limit.

Fix: Add cursor-based pagination (next_page_token pattern) with a default page size of 25 and a hard ceiling of 100. Return 429 Too Many Requests when rate limit exceeded.
