02 · YOUR CHALLENGE, ANSWERED

“Will slicing the TS really work, or is it diverging from Software Factory?”

It is a fair challenge and it deserves a direct answer: it is not a divergence — it is Software Factory applied recursively.

Software Factory’s scope is one feature. Its whole run — product doc, architecture, program design, slices — lives under a single docs/plans/<feature-slug>/. It has no opinion about what happens when you have six features, because it was never asked that question.

What we have called the epic gate is exactly a Software Factory run. One epic = one feature = Gate 1 product framing, Gate 2 architecture, Gate 3 program design, Gate 4 slices. Nothing in it is modified. The BS is a new tier above that scope, not a change to it.

SOFTWARE FACTORY, UNCHANGED
docs/plans/<feature>/ 01-product.md 02-architecture.md 03-program-design.md 04-slices.md

One feature. Four gates. Slices at the end.

SAME THING, INSIDE AN EPIC
TS-E1.md §Fit / Endpoints / Data / Flow ← 02 §Files / Types / Call stack ← 03 §Test plan 04-slices for E1 ← 04

The BS carries Gate 1 for every epic at once, because the product framing is initiative-wide.

But the challenge does expose a real risk

Just-in-time TS only works if epics are genuinely separable. If E3 needs a contract that E1 quietly decided differently, you find out late — exactly the failure JIT was supposed to avoid.

Mitigation, now part of the design: the BS declares epic dependencies, and each skeleton TS names the cross-epic contracts it exposes or consumes. Those contracts are frozen at BS approval and are the one part of a skeleton that later detailing may not silently change — altering one is a backtrack to G1, with re-approval.

03 · TIER MODEL

One initiative, N features, M slices

A feature is an epic, one to one. An epic is itself a vertical slice of the product — it ships something a user can see, and it must always be testable. That is the admission test for an epic: if you cannot state how you would prove it works, it is not an epic yet, and the BS is not finished.

05 · THE LOOPS

Epic gate: hard, with feedback going back to GREEN

Your two notes on Q3 combine into this. When the last slice of an epic passes, the epic is scored against the BS criteria. Below 0.90 it does not close — a remediation slice is created and the epic-level validator feedback goes back to the GREEN agent to incorporate and improve, until done.

One difference from the slice loop, deliberately: the slice loop escalates after 3 attempts, but you said the epic should run until done. So epic remediation has no automatic escalation. It does have a human circuit breaker — after every 3 remediation slices the run stops and asks you whether to continue, re-scope the epic, or accept the gap. Looping without a check-in is how an agent burns an afternoon on an unreachable criterion.

0.0 / 0.5 / 1.0

Three values, not a continuum. A five-point scale lets a validator split the difference at 0.7 on anything ambiguous, which is how a marginal slice drifts past the gate.

CRITICAL override

A failed critical criterion blocks acceptance regardless of average. Four perfect criteria plus one broken auth check averages 0.80 and must never ship.

VOID ≠ low score

A test edited, skipped, weakened, or one that would pass against pre-change code — voids the run. Rerun from RED. It does not consume an attempt, because what was measured was not the thing.

06 · LIGHT PATH

One epic means one document and no panels

You were blunt about this and you were right: a three-epic initiative running 1 refute panel + 3 research panels + 3 skeptics is heavier than many features deserve, and “we should absolutely not run the 3 research + skeptics panel if there is only one epic”.

The slice loop and the ≥ 0.90 blind gate never switch off — they are the point of the skill. What the light path removes is the design apparatus that only pays for itself when several epics must stay coherent with each other. Research still triggers on a new library, external API, or version bump, because that risk does not scale with epic count.

Blindness is enforced three ways, not by location alone

You chose an in-repo hidden folder, so the path alone protects nothing. Every implementer prompt carries “do not read anything under .cobuilder/”; the implementer is handed the slice description, never the rubric path; and if it reads the rubric anyway the score is voided rather than lowered — rerun from RED at no attempt cost. The one carve-out is the validator’s feedback.md, which carries guidance but never criteria.

09 · SHIPPING

Where the workflow scripts live

A skill directory is not a workflow discovery path. Named workflows resolve from a project’s .claude/workflows/; plugins auto-discover a workflows/ directory. There is no ~/.claude/workflows/.

Your note on rubric drift — “we can define this all in a workflow for how to run the BS/TS loop” — means there are now two scripts, not one:

WORKFLOW 1

spec-loop.js

Runs G1–G3: draft BS → refute panel → skeleton TS → per-epic detail → research → refute → refine → skeptic → rubric authoring. Also owns rubric sync: when a BS criterion changes, an agent re-derives the affected epic and slice rubrics rather than leaving them to drift.

WORKFLOW 2

slice-loop.js

Runs G4: red → green → validate per slice with the retry counter and escalation cutoff enforced in code, then the epic rubric and its remediation loop.

Now → planned

Now: the skill copies both scripts into the target repo’s .claude/workflows/ on first use, with a version header so a newer skill overwrites an older copy. Planned: convert cobuilder-factory to a plugin — plugins auto-discover workflows/, skills/, commands/, and agents/, which removes the per-repo copy and adds /cobuilder:* commands. This will be documented in the skill so the copy-on-first-use reads as a bridge, not a destination.

10 · RISKS, REVISED

What is left after your review

Ceremony exceeds the work resolved

Light path (§06). One epic collapses to a single spec with no panels and no epic rubric.

Rubric drift across tiers resolved

Epic rubrics cite BS criterion IDs, and spec-loop.js owns rubric re-derivation when a criterion changes. A mismatch is a gate failure, not a warning.

Blindness is honour-based accepted

Marked an accepted risk per your note. Nothing mechanically prevents an implementer reading .cobuilder/; the void rule punishes it after the fact and detection depends on the validator noticing.

Cross-epic contract drift new

Raised by your TS-slicing challenge. JIT detailing can quietly redefine a contract another epic depends on. Mitigated by freezing declared contracts at G1, but the mitigation is a rule, not a mechanism — it depends on the skeleton naming the contracts honestly.

Removed: “0.90 is unreachable on integration-heavy epics” — you said it is not, so it is gone rather than restated.

11 · DESIGN MODE

The division of labour, settled

My rev 2 recommendation said design mode should replace G1. Your amendment to ADR-0011 draws the line more precisely, and better: design mode does not do epic decomposition — that is the factory’s G1 work. Design mode’s stage 7 asks only whether this is one PR or several, captures the epic slugs when several, and creates the first branch.

So G1 splits in two. That keeps design mode from growing a second, weaker planning tier, which is the reason you gave and it is the right one.

Corrected: the join contract path

Rev 2 named the contract as exports/design-<name>/intent.json. Your cross-plan warning is correct — phase 4b moves it. The contract is docs/architecture/designs/<name>/intent.json, and both plans must change together or the contract breaks silently. This is now recorded in the ADR rather than left in a review page, precisely because a file path agreed in a browser is a path nobody can find in six months.

What the factory writes back

Design mode owns goal.json. The factory fills in the parts only decomposition can know, after G1b:

"epics": [ {"id": "E1", "slug": "guest-checkout", "outcome": "<testable criterion>", ← factory writes "branch": "design/checkout/guest-checkout", "pr": 42, "state": "merged"}, {"id": "E2", "slug": "saved-cards", "outcome": "<...>", "branch": null, "pr": null, "state": "planned"} ], "stage": "partially-delivered" ← delivered when every epic has a merged PR

Branch convention design/<design-name>/<epic-slug>, which makes the join a prefix parse. A single-epic design keeps the plain design/<name> form, so the common case adds nothing to remember. That aligns exactly with the factory’s light path.

One question your amendment leaves open — my answer

Rev 2 asked whether the factory still runs its refute panel when design mode already challenged the approach (Q5, unanswered). The division of labour answers it: yes, and on a different target. Design mode’s stage 4 challenges the approach. It never challenges the epic decomposition, because it does not produce one. So the factory’s refute panel moves to what it is now uniquely positioned to attack: are these epics genuinely independent, is each one testable, is one missing, do the declared cross-epic contracts hold? No signal is paid for twice.
