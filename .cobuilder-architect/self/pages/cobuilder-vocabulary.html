Working session record

A vocabulary for a plugin whose names had started to drift

This session reviewed cobuilder-architect's architecture and PR #11, then spent most of its length on something the review surfaced: the same words meaning different things across the odyssey and architecture skills. What follows is the resolved vocabulary, the ten decisions still needing an ADR, and the architecture those decisions produce: five sibling plugins in one cobuilder repository, every existing file given an owner, and a five-phase path from here to there.

Session scope Architecture review of cobuilder-architect · review of PR #11 (design/design-mode → master) · naming and structure discussion carried across the remaining turns.
01

Decisions carried, pending an ADR

Ten separate calls came out of this session. Each stands on its own evidence and should not be folded into one document.

1 · Repo topology — three sibling plugins, one repository

Amends ADR-0013

One cobuilder repository, three plugin packages, none nested inside another. The architect and pull-request pillars stop being two skills inside a single cobuilder-architect manifest and become sibling directories in their own right, alongside cobuilder-implement. Each carries its own plugin.json and installs on its own. architect’s design mode keeps joining cobuilder-implement through intent.json on disk — never a code call, never a shared install.

ADR-0013 rejected a hard dependency and a code-call join between the design step and the build step, reasoning that the build step “must run in any harness.” It never ruled on physical repo location. This resolves the two-versus-three-plugin question from an earlier round of this document: three, each independently installable, all in one repository for one visible lifecycle.

2 · Command renaming, applied uniformly

New ADR

Submit splits along a seam its own docs already name — “the author’s side… and the reviewer’s side.” The narration sweep gets its own name instead of inheriting Submit’s. Every mode name is a bare verb — generate, assess, review — and decision 1 supplies the qualifier for free: /cobuilder-pr:generate, not a hyphenated compound.

pull-request:generate-pr repeated a word the plugin boundary already carries. pr-story removed the repeat but broke the fit test for two of its three modes — only review produces a story; generate and assess do not. Once the pull-request pillar is its own plugin rather than a skill sharing a manifest, the slash-command prefix does the qualifying job on its own, and no mode name needs a suffix at all.

3 · Fold pull-request’s design flow into cobuilder-architect:design

Amends ADR-0011 & ADR-0013

Odyssey’s interview-and-challenge design flow merges into the architecture skill’s own design mode, which already wraps it as an internal stage. The merged mode keeps producing intent.json, and its final step names cobuilder-implement as the next tool to run.

This is a real amendment, not a rename: ADR-0011 and ADR-0013 chose to keep the two design flows separate on purpose, reasoning that Odyssey’s version does more — framing, exploration, and the challenge — than the architecture skill’s exploration pass alone. Reopening that call needs the same decision-record path those two used. It should run through that path — design this restructuring with cobuilder-architect:design itself, once decision 2 is approved, rather than plan it outside the tool that exists to plan it.

4 · Baseline, View, and Publish belong to neither pillar alone

Resolved this round

Baseline moves to the architect pillar — it already overlaps cobuilder-architect:describe at a lighter tier. View and Publish stay shared (see decision 5). The viewer’s own chrome switches between data-mode="designs" and data-mode="prs" as one toggle on one page (viewer/index.html:640-641), and every published artifact inlines window.DESIGNS beside window.ODYSSEY (export_artifact.py:369). Neither reads as PR-only or architect-only; both read the one bundle both pillars write into.

A plugin named “pull-request” that still owned View and Publish would repeat the exact fit problem “odyssey” had — a name that covers most of its modes but not all. Leaving View and Publish outside both pillars, as bundle-level utilities, is what lets the pull-request pillar fit all three of the modes it does own.

5 · cobuilder-artifact ships as a fourth plugin, joined by declared dependency

Verified against docs

view and publish become their own plugin, cobuilder-artifact, rather than living inside cobuilder-architect or cobuilder-pr. Both of those declare it in their own plugin.json:

"dependencies": ["cobuilder-artifact"]

Installing either plugin auto-installs cobuilder-artifact alongside it. Each then calls Skill("cobuilder-artifact:view") / Skill("cobuilder-artifact:publish") directly — the same fully-qualified, namespaced call this repo already uses today for Skill("cobuilder-architect:mermaid") and Skill("cobuilder-architect:ste-writing"), just crossing a plugin boundary instead of a skill boundary inside one plugin.

A symlinked skill directory was the proposed mechanism, and it does work: the plugin loader dereferences a symlink that points elsewhere within the same marketplace repository, copying the target’s content into each installing plugin’s own cache, specifically to let “a meta-plugin’s skills/ directory link to skills defined by other plugins in the marketplace” (Plugins reference). But that mechanism solves a different problem — sharing skill content into a namespace that does not otherwise have it. It does not guarantee cobuilder-artifact gets installed at all. The dependencies field does exactly that, is part of the documented manifest schema, and needs no file duplication into either neighbor’s cache. Verified directly against Plugins reference and Create plugins, not assumed — an initial research pass flagged the dependency field as undocumented, which a direct fetch of the reference page shows is out of date.

6 · Every plugin carries the cobuilder- prefix

Verified against docs

architect becomes cobuilder-architect and pull-request becomes cobuilder-pr, matching cobuilder-implement and cobuilder-artifact, which already carried the prefix. All four plugin names are consistent now, not three prefixed and two bare.

marketplace.json validation only catches a duplicate plugin name within one marketplace — the error is literally “Duplicate plugin name ‘x’ found in marketplace,” scoped to one file (Plugin marketplaces). Two different marketplaces can each publish a plugin named architect with nothing stopping them, and skill namespacing runs off that bare name field — installing both in one session would collide on /architect:*. Generic single-word names carry that risk; cobuilder- removes it the same way it already protected cobuilder-artifact. pr, not pull-request, because this document already uses “PR” as the working abbreviation throughout — PR #11, “opens a PR,” and so on — so cobuilder-pr matches vocabulary already in use rather than introducing a second one.

7 · A fifth plugin, cobuilder-full-lifecycle, bundles the other four

Resolved this round

A fifth plugin, cobuilder-full-lifecycle, lists cobuilder-architect, cobuilder-pr, cobuilder-artifact, and cobuilder-implement as direct dependencies — all four named explicitly, not just two of them left to carry the others along underneath. One /plugin install cobuilder-full-lifecycle installs the whole family; each of the four stays separately installable for anyone who wants less.

Naming all four directly, rather than two and trusting their own nested dependency on cobuilder-artifact to carry through, matters because transitive dependency resolution is the one part of this mechanism the documentation does not fully confirm. It describes enabling a plugin’s declared dependencies “transitively at the same scope,” but that quote is scoped to the plugin enable command, not shown end-to-end for install. Listing every dependency directly sidesteps the question instead of resting on the answer. What remains genuinely unconfirmed: a plugin shipping no skills, commands, or agents of its own — only a manifest and a dependencies list — is not a pattern the documentation states outright works, though name being the only required manifest field points that way. Worth a claude plugin validate pass on a draft manifest before this ships, not assumed. Decision 10 removes the exposure regardless.

8 · Two mechanisms, not one: dependencies co-install, symlinks share files

Refines decision 5

The dependencies field guarantees that cobuilder-artifact is installed alongside cobuilder-architect and cobuilder-pr. It does not give any of them access to another’s files. Shared Python and shared skills travel by a second mechanism: a real directory under shared/ at the repository root, symlinked into each plugin that needs it, dereferenced into that plugin’s own cache at install time.

The reference page is explicit that a cached plugin cannot read outside itself: “Copied plugins cannot reference files outside their directory. Paths that traverse outside the plugin root (such as ../shared-utils) will not work after installation because those external files are not copied to the cache” (Plugins reference). ${CLAUDE_PLUGIN_ROOT} resolves to one plugin’s own cache directory and nothing above it, so today’s single flat scripts/ tree cannot simply be pointed at from four plugins. The same page names the fix: a symlink elsewhere within the same marketplace is dereferenced, and the target’s content is copied into the cache in its place. The cost is honest and worth stating — every plugin that needs _bundle_meta.py ships its own copy of it. That copy is what makes the version-skew rule in decision 9 load-bearing rather than theoretical.

9 · The bundle is the only seam between plugins

New ADR

No plugin calls another plugin’s code, imports its modules, or invokes its skills. They read and write one versioned directory: .cobuilder-architect/<target>/. cobuilder-architect writes designs.js and adrs.js. cobuilder-pr writes story.json, diffs, diagrams, and audio. cobuilder-artifact reads all of it and renders. Each plugin stamps its own generator_version. verify_bundle.py gates on schema_version.

This is what the split actually costs and what makes it survivable. Four separately-installable plugins can be four different versions on one machine, and each carries a vendored copy of the schema constant per decision 8. A plugin that meets a bundle newer than it understands must fail loudly on the version gate rather than write a half-shape into it — the existing SCHEMA_VERSION_KNOWN set already does exactly this and becomes the split’s safety rail rather than a migration convenience. The seam is also already real: the viewer’s Designs / Pull requests toggle reads two globals written by what will become two different plugins, and neither writer knows the other exists.

10 · cobuilder-full-lifecycle ships a SKILL.md, so it is not an empty plugin

Resolved this round

The bundling plugin carries one skill of its own: an orientation document naming the four plugins, the order the lifecycle runs in, and which command to reach for at which stage. The dependencies list stays exactly as decision 7 set it — all four named directly.

This earns its place twice. It retires the one open item decision 7 left behind: a plugin with a skill is an ordinary plugin, so the unconfirmed zero-component pattern stops being load-bearing and claude plugin validate becomes a routine check rather than a gate. And it fills a real gap the split creates — a user installing four plugins at once meets thirteen commands across four namespaces with nothing telling them that design precedes implement precedes generate precedes review. That orientation exists nowhere else once CLAUDE.md is no longer one file describing one plugin.

05

Migration path

Five phases, ordered so that the repository installs and runs at the end of each one. Nothing here needs a flag day.

  1. Land the vocabulary and the renames inside today’s single plugin

    Split submit into generate and assess, rename the narration sweep to review, fold odyssey’s design mode into the architect pillar, and move baseline across. One plugin still, one manifest, no packaging change. Every decision from 1 through 4 is testable at the end of this phase.

  2. Extract shared/ and prove the symlink dereference

    Move the four bundle-core scripts and the two shared skills into shared/, symlink them back into place, and confirm an installed copy still resolves them. This is the one phase that can fail on a platform behavior rather than on our own code, so it goes early and alone.

  3. Split the manifests

    Create the five plugin directories, five plugin.json files, and one marketplace.json listing all of them. Wire the dependencies fields. Run claude plugin validate on each.

  4. Harden the seam

    Make every plugin stamp its own generator_version, and make the schema_version gate fail loudly rather than proceed when a bundle is newer than the reader. Until this lands, a mixed-version install degrades silently — which is the only genuinely new failure mode the split introduces.

  5. Write the orientation skill and the ADRs

    cobuilder-full-lifecycle’s SKILL.md per decision 10, and the decision records this document has been deferring throughout: new ADRs for decisions 8 and 9, amendments to ADR‑0011 and ADR‑0013 for decision 3, and to ADR‑0013 again for decision 1.

06

PR #11 — findings that held up

design/design-mode → master, unmerged. Three claimed fixes, checked directly against the diff rather than the PR body.

Confirmed verified in code

The ste-writing skill-resolution fix is complete at all three sites the PR touched — SKILL.md, design-mode.md, story-mode.md — each now falling back to a direct file read on Unknown skill. The multi-design branch resolution in Submit mode now collects every matching design and asks the author which ones a PR delivers, rather than silently taking the first match. ADR-0013’s file-only join is reasoned, not assumed.

Found during this review missed by the PR

A fourth, unguarded call site: CLAUDE.md’s own Writing standard section instructed Skill("ste-writing") with no fallback. It only worked here because this repo carries a second copy under .claude/skills/ — the same coincidence that hid the other three. Fixed in this session.

The plugin manifest names a repository that is not this one: plugin.json declares github.com/bjornslib/cobuilder-architect; the actual git remote is github.com/bjornslib/prodyssey.git. Not yet fixed.

Open, self-flagged by the PR

The cobuilder-implement validator judges test adequacy after executing the suite — a single LLM judgment call at a 0.90 gate. The PR’s own reasoning against an “amnesia” two-pass design applies here too: one policy scoring itself carries correlated error. Worth a stress test before implementation starts.

07

Open questions

Every naming and structural question raised this session is resolved. Two things remain unverified, and both are platform behavior rather than design.

The symlink dereference, end to end blocks phase 2

The reference page states that a symlink elsewhere within the same marketplace is dereferenced and its target copied into the cache. The whole shared/ layer rests on that sentence holding for a directory of Python that a skill later executes through ${CLAUDE_PLUGIN_ROOT}, not only for a skill directory. Install a two-plugin draft from a local marketplace and read what actually lands in the cache before committing phase 2. If the dereference does not cover it, the fallback is a build step that copies shared/ into each plugin before publish — more machinery, same result.

Transitive dependency resolution already routed around

Still unconfirmed for plugin install as opposed to plugin enable. Decision 7 names all four dependencies directly so that nothing depends on the answer. Recorded here only so a later reader does not mistake the redundancy for an oversight and tidy it away.

Retired this round

The empty-plugin question is closed by decision 10: cobuilder-full-lifecycle ships a skill, so it is an ordinary plugin and never tests the pattern.
