3. How submit mode finds the design round 2

You asked the right question: what actually connects a design to the pull request that implements it? Answer — the branch name, and nothing else.

The resolution rule

Submit mode already computes a branch slug for exports/branch-<slug>/. It gains one step before that:

BRANCH=$(git rev-parse --abbrev-ref HEAD)
# design/streaming-ingest  ->  streaming-ingest
NAME=${BRANCH#design/}
DESIGN="$BUNDLE/exports/design-$NAME"

# fall back to goal.json.branch on any branch
# whose name does not carry the prefix
[ -d "$DESIGN" ] || DESIGN=$(grep -l "\"branch\": \"$BRANCH\"" \
    "$BUNDLE"/exports/design-*/goal.json | xargs -r dirname)

The design/ prefix is the fast path. goal.json.branch, written at stage 7, is the authoritative record — so an engineer who renames the branch does not break the link.

What submit mode does with it

1. Skips the cold interview. intent.json is loaded as the starting hypothesis. The interview asks only what changed between the design and the build, which is usually one or two topics rather than six.

2. Measures drift for the first time. review-mode.md §7 defines a drift array that has never had a baseline to compare against. The design's ADR and its constraint_introduced now supply one. "The design established invariant X; the branch does not hold it" becomes a finding with evidence.

3. Carries the design forward. The ADR draft moves into adrs.json under the real PR number, with its rejected options already written.

no design present — submit mode behaves exactly as it does today. This is additive.

Name & Outcome + duplicate search

The engineer states the outcome they want and names the design, before the agent reads a file. Then a subagent searches every existing exports/design-*/ for a design that already covers this problem. The match is semantic, not a keyword grep. The subagent reads goal.outcome, intent.problem, and the ADR draft of each candidate and judges whether it addresses the same problem — two designs can share every word and solve different things, or share none and collide completely. A grep over titles would find neither case.

On a hit, show the match and its stage, and let the engineer choose: resume it, supersede it (the old one gets stage: "superseded" and a pointer to the new one), or proceed anyway because it is genuinely different. This catches the re-discussion nobody remembers having, which a name-collision check never would.

6. Stage 4 — the Challenge gate

Grill the engineer on risks that surfaced which they had not considered, and on anything that ought to be done differently to how they suggested it. After your cuts, this stage is the sole producer of the ADR's Considered Options section.

What it does

1. Confront the unconsidered risks. Every risk exploration surfaced that does not appear in intent.risks gets stated with its evidence, and put to the engineer directly: accept, mitigate, or dispute. The answer is recorded.

2. Contest the approach. Where a survivor option beats intent.approach on a stated criterion, say so and argue for it. The engineer may overrule — and that overrule is recorded as a rejected option with the engineer's own reason, which is the ADR field the retro-extraction path always loses.

3. Name what nobody checked. Anything the agent could not verify goes on the record as an open question, never as a silent gap.

What keeps it honest

Evidence or silence. review-mode.md §2 holds with one inversion: no path:line exists yet, so a challenge must cite an ADR id, a district id from inventory.yaml, a stack-card boundary rule, or a corpus principle. A challenge with no citation does not get raised. This is the guard against manufactured disagreement.

Disagreement is allowed to end. Cap each challenge at a few exchanges. If it does not resolve, record both positions and move on.

An empty challenge stage is valid, but must be stated. "Exploration surfaced no risk outside what you already named" is a sentence the engineer should read, because it proves the stage ran.

The failure this now guards against is worse than in round 1. With no interview question asking for rejected options, a skipped or toothless Challenge gate leaves intent.alternatives empty. The mode would then emit an ADR that records one choice instead of a decision — readable, well-structured, and worthless. The derived goal.min_work must therefore block completion until this stage has run and its outcomes are recorded.

The designs view

The viewer today navigates a PR timeline. It gains a second mode — a list of every design in the bundle with its name, stage, round count, and branch, and a reading surface for one design: the ADR draft, the level 1–3 diagrams, the envisioned PR, and the design-stage assessment.

Cost is low, because the pattern already exists. A data/designs.js file populating window.DESIGNS is the same sibling-script-tag pattern story.js, manifest.js, adrs.js, and diagrams.js already use. The assessment sheet renders with the component the viewer has. No new dependency, no build step, and it survives export_artifact.py unchanged — a design is text and Mermaid, so it carries no PNG weight against the 16 MiB budget.

agreed: not a Lavish clone Element-level annotation and a send-to-agent channel would be a genuine project of its own. Recorded as a future option, not scoped here.

What bounds the loop

Multiple rounds is where an agent session degrades: context compacts, the objective blurs, and the loop starts agreeing in order to finish. Three guards, all read from goal.json:

Durable objective. Re-read the file and restate the outcome at the top of every round. The file is the memory; the conversation is not.

Churn detection. Hash the ADR draft plus the option set each round. Two consecutive rounds with no material change means the loop is circling — say so, name the unresolved disagreement, and ask the engineer to decide. Do not run a third.

Minimum work. Block "ready" until the derived threshold is met: alternatives explored, boundary rules checked, Challenge run and recorded, diagrams authored.

Why material feedback returns to stage 3, not stage 5. A real objection usually invalidates an option or surfaces a constraint, which changes what should have been explored. Returning only to drafting produces a rewritten document defending the same choice. Cosmetic feedback — wording, diagram layout, ADR ordering — goes straight back to stage 5. The agent states which it chose; the engineer overrules it when it guesses wrong.

10. Risks, and what is still open

Failure modes

high  The agreeable design

The agent explores, finds nothing that contradicts the engineer, and writes their opening idea up as an ADR. It reads well and is worth nothing. Now more likely than in round 1, because no interview question asks for rejected options any more. Guard: derived goal.min_work blocks completion until Challenge has run and recorded outcomes; an empty Challenge stage must be stated as an explicit finding.

high  Prediction read as observation

A design-stage finding cites no code because none exists. Rendered like a pre-stage finding, a reviewer reads a guess as a check. Guard: kind: "prediction", and a distinct visual treatment in the designs view.

medium  The lost design link

The engineer renames or rebases the branch and the design becomes unreachable. Guard: §3's two-step lookup — the design/ prefix is the fast path, goal.json.branch is authoritative, and submit mode degrades to today's behavior when neither resolves.

medium  Duplicate-search false confidence

The stage 0 subagent misses an existing design, and the engineer trusts the "no match" answer. Guard: report what was searched and how many designs exist, never a bare "none found". The engineer chooses; the subagent only surfaces.

low  Branch creation surprises the engineer

Stage 7 writes outside .prodyssey/, which only submit mode's push otherwise does. Guard: AskUserQuestion confirmation, local branch only, never a push, unreachable under --non-interactive.

low  Auto-baseline surprises on a large repo

Running baseline unasked is right, but it is not instant on a big history. Guard: say it is running and why before it starts, and report the elapsed time. Never run it silently.
