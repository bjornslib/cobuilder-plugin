A port between CoBuilder and the task system

Source of record: docs/architecture/designs/beads-storage/tracker-port-exploration.md. Exploration only. Nothing here is decided, and no design file changed except that note.

1. The three questions

QuestionShort answer
i. How do we integrate with different task systems?One adapter per tracker. A CLI adapter for beads (bd), an HTTP adapter for Linear (GraphQL) and for Jira (REST). Scripts call them, as scripts call git and gh today (ADR-0016).
ii. What is the abstraction?A TrackerPort of neutral operations plus a capabilities() report. Adapters implement it.
iii. How do results map to our data?Every adapter returns the same neutral TrackerRecord list. One shared projector turns it into the entities and joins that build_index.py builds today.

2. The proposed layers

Solid: build in this program. Dashed: later programs. The port also carries the neutral record: id, kind (program, epic, slice, pr), parent, blocked_by, lifecycle (open, in progress, closed), envelope, external_ref, updated_at.

Finding 1. The work graph (parent, blocks, lifecycle) exists in every tracker. The custom-data slot for score, attempts, and gates differs in each. The port must separate the two.
Finding 2. Linear accepts only a string or a number as a metadata value. The envelope rule allows a list of paths (cb.evidence). A Linear adapter must encode a list as a JSON string, or the envelope keeps one path field for each attempt.
Finding 3. The goal says the index rebuild must not need the network. Linear and Jira do. An adapter pull writes a local snapshot, and build_index.py reads only the snapshot.
Finding 4. bd ships its own sync commands: bd jira sync, bd linear sync, and others (help text read, not run). I do not know whether they carry metadata.cb.

4. Options

Recommended

A. Port with adapters

  • CoBuilder owns the seam in shared/tracker/.
  • Build now: port, record, projector, fake adapter, contract test, beads adapter.
  • Later programs: Linear and Jira adapters, each opened by a smoke test of its orange rows.
  • Cost: the port must not take the shape of beads. The table above is the guard.
Interim path

B. Beads only, use its bridges

  • No new code. A team runs bd jira sync or bd linear sync.
  • Beads stays mandatory, even for a team that works only in Jira.
  • Envelope fidelity unverified. Two systems hold state, and "the issue wins" has no answer when a person edits Jira.
  • Fits a read-mostly mirror, not a system of record.
Not advised

C. Beads direct, extract later

  • Fastest start.
  • Every caller holds bd calls, so the later extraction rewrites them all.
  • With one implementation, the seam is a guess.
Rejected on record

D. An MCP server per tracker

  • ADR-0016 and CLAUDE.md principle 5: no plugin ships an MCP server.

5. What changes if you choose A

  • ADR: ADR-0031 narrows to "beads is the first adapter and holds its mapping". A new ADR records the port.
  • Goal: "bd is required for writes" becomes "a configured tracker adapter is required for writes". The success measure becomes one "next slice" call. On beads, that call is bd ready.
  • Epics: a port epic comes first (port, record, projector, fake, contract test). The beads seed, the read model, and the write model then build on it.
  • Files: intent.json, goal.json, assessment.json, narrative.json, the three diagrams, the runtime SVG, and the glossary all change. I refreshed them earlier for beads only, so they need a second pass.
