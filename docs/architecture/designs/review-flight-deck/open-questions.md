For the `review-flight-deck` design. Written 2026-09-02.

what `intent.json`, `assessment.json` and ADR-0022 already settle.

A question here is open for one of two reasons. Either nobody has made
the call, or the call rests on a measurement nobody has taken. Each row
says which.

## 2. Questions this session opened

These four came from measurement, and none of them existed when the
design was written.

### Q1. No common ancestor

`git merge-base --octopus` over this repository's 18 pull request heads
returns nothing. Pull request 11 descends from a second root, `a7fc1d5`.
The scaffold commit `0c099be` is the other root. The two join at the pull
request 11 merge.

ADR-0022's `maps_to.rule` says a path is simulated against the common
ancestor of the open branches. For a set like this one, that value does
not exist.

Git makes the failure quiet. `git merge-base --octopus` prints nothing
and exits 1, with no reason. `git merge-tree` is louder, and exits 128
with `fatal: refusing to merge unrelated histories`.

Two candidate answers:

- **(a) Name it a block kind.** A branch with no common ancestor joins
  the superseded and conflict cases on the front page. The path carries
  the rest of the set.
- **(b) Partition the set.** Group the branches by shared base, and
  report one path per group. The research reference proposes this in its
  section 3.3, and marks it as untested.

Option (a) is smaller and matches a surface that already exists.
Option (b) recovers more of the set.

**Option (b) is harder than it looks, and the spike probe proved it.**
"This set has a common ancestor" is not a transitive property. Pull
requests 1 and 12 are related. Pull requests 11 and 12 are related. Pull
requests 1 and 11 are not, and the octopus base of all three is empty.

So grouping branches into connected components does not work. A component
can be pairwise connected and still have no base. The partition needed
here is a covering problem, not a connected-component problem.

`spike/probe_repo.py` now reports both. It finds the components, and then
splits any component with no base into a co-based subset plus the
outliers. The split is greedy, so it returns one valid answer rather than
the largest one. On this repository it drops pull request 11 and finds
the other 17 share base `8646447`.

### Q2. Which ancestor, when several are valid

`0c099be` is an ancestor of every head except 11. It is not the *common*
ancestor. The octopus base of the set without pull request 11 is
`8646447`, and without pull requests 1 and 11 it is `90f106f`.

Simulating from `0c099be` is correct but wasteful. It replays 18 commits
and 65 changed files of work that already merged.

ADR-0022, `intent.json`, `narrative.json`, `pr-draft.md` and the
prototype all name `0c099be` as the base. That description is wrong, and
the records need a correction once Q1 and Q2 are settled together.

### Q3. A conflict in a derived file

Testing this branch against pull request 19 gives a real conflict in five
files. All five are generated by `shared/build_index.py`:

```
.cobuilder-architect/self/data/adrs.js
.cobuilder-architect/self/data/adrs.json
.cobuilder-architect/self/data/designs.js
.cobuilder-architect/self/data/index.js
.cobuilder-architect/self/data/index.json
```

Neither side authored a conflicting line. Both sides regenerated the same
projection from different inputs. A human choosing a side would be doing
the wrong job. Re-running the generator after the merge resolves all five.

The design names two block kinds, superseded and conflict. It does not
name this one. A flight deck that reports five red files, where one
command fixes all five, teaches reviewers to distrust it.

The open part is how the mode knows a file is derived. Three options:

- A declared list per repository, in configuration.
- A convention, such as everything under the bundle directory.
- A test: re-run the generator after the merge, and see if the conflict
  disappears.

The third is the only one that needs no configuration, and it is the most
expensive.

### Q4. The ordering algorithm

The research reference surveyed 20 tools. None of them orders an
unordered set. There is no algorithm to copy and no reference
implementation to read.

This is the design's real contribution, and it is the whole of its risk.
It is also the one part with no prior art to fall back on.

The spike plan tests candidate heuristics against a baseline. Until that
runs, the design assumes a capability nobody has shown to work.

### Q5. A corpus

This repository cannot validate the design. Of 153 pairs of pull request
heads, 139 are ancestor and descendant, 11 are disjoint, and 3 are
genuine three-way merges. All three merge cleanly. Zero conflicts exist
in the whole history.

Every branch here was cut, merged, and the next cut from the result. The
scenario of many branches open at once never happened. A replay against
this history returns zero conflicts whatever order it uses.

The live open set is one pull request. No ordering problem exists today.

## 3. Questions the design already carried

### Q6. Naming

"Stack" means a chain an author declared in advance. Every tool in the
survey uses it that way. Our set is assembled after the fact, by us, from
branches nobody coordinated.

`CLAUDE.md`'s Vocabulary section sets the rule for this family. One name
for one thing. A distinct word is needed before the mode ships, so that
no reader takes `pr:flightdeck` for a Graphite clone.

### Q7. Whether a reviewer trusts a proposed order

The load-bearing claim, and it rests on judgement. `assessment.json`
names it in `regret_risk`. Validation covers the merges. It does not
cover whether the order is the one a reviewer would have chosen unaided.

### Q8. A branch that moves mid-rollout

A replay is a snapshot against recorded heads. A push after the run
invalidates it. The design does not say whether the path stops, re-runs,
or carries on.

### Q9. How many paths

The design says at least three. Nobody has tested whether two is enough
and four is noise.

### Q10. Auto-merge rules

The mode reads which pull requests a team's own rules already handled.
The split shown in the prototype is invented. Nobody has looked at a real
set of rules.

## 4. Questions from the assessment

### Q11. Three new ledger line kinds

ADR-0019 fixed the ledger vocabulary at comment, reply and state.
`fold_threads` skips a line it does not recognise. A path acceptance, a
bundle merge and a blocked-pull-request decision are none of the three.
Each needs its own projection, and nothing enforces that a future reader
handles all three.

### Q12. A staleness marker

The replay projection carries no marker. A reviewer opening the surface a
day later sees a validated path, with no sign that four of its branches
moved. `publish-manifest.json` already solved a version of this with a
content hash. Nothing here reuses it.

### Q13. Who owns the open-pull-request entity

Epic F1 duplicates the first epic of the `inflight-record-store` design.
Both need open pull requests as entities in the record index. Building it
twice is the likely failure. Whichever design ships first should own it,
and the code belongs in `shared/`.

## 5. Deferred, and deliberately so

### Q14. Runner credentials

The runner is the first thing in this plugin family that writes to a
remote. Its credentials and its permissions sit in the adopting
repository, outside this design.

### Q15. Integration branch cleanup

A path of N bundles leaves N branches behind. Nothing here deletes them.
