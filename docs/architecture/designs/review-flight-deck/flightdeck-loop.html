2. The blocker

This family ships no way to run itself

Constraint collision

The five plugins ship no agents, no hooks, and no MCP servers. That rule is deliberate, and it exists so no plugin touches another session's permission surface. A mode cannot start itself on a pull request event.

Automatic triggering must therefore come from outside the plugin. Three places can supply it. This repository has no .github directory today.

A. A workflow in the target repo

A GitHub Action runs the mode on pull_request events, and commits the proposals into the bundle. The plugin ships a template. The user installs it once, by choice.

Truly automatic. The plugin still ships no hook.

B. A scheduled session

A routine wakes a session on an interval and runs the mode. Nothing installs into the repository. The proposals lag the pull request by up to one interval.

Near-automatic. It costs a session per run.

C. Run it when review starts

The reviewer opens the deck and the mode runs first. No automation at all, and the proposals are always current at the moment somebody reads them.

Not automatic. It is the fallback, not the goal.

Option A meets the intent and keeps the install rule. It also adds a first .github/workflows/ file to a repository that has none, and it needs a credential in CI. Option C works on day one and needs nothing.

3. A real run

26 August 2026, three pull requests open

Pull requests 16, 17, and 18 were open together. 17 and 18 share one head branch, rename-plugins-drop-cobuilder-prefix. That fact alone changes the right review order, and no reviewer sees it in a pull request list.

4. What to build

Four epics, and three of them already exist elsewhere

The revised intent reuses more of this repository than the old one did. Only the proposer is new work.

EpicWorkReusesState
F1 Read the open set. List open pull requests with their head branch, files, and design. The inflight-record-store design owns this gap. Its first epic is the same work. shared
F2 Generate several proposals. Each names a review order, a reason, and the evidence. divergent-exploration.md already generates competing options and criticises them. new work
F3 Write the narrative and the diagram. One short story and one Mermaid file per proposal. The story-mode and mermaid references, and build_diagrams.py. Both key on a pull request number and need a proposal key. adapt
F4 Show the proposals and record the pick. Read-only render, one ledger line on choice. The viewer's existing view modes and the ledger from ADR-0019. adapt

The six epics I recorded yesterday collapse into these four. The region walk moves inside F2 as the evidence a proposal cites, and it stops being a reviewer-facing step.

5. One decision

Pick the trigger, and the rest follows

Every other question I raised yesterday is now answered by the revised intent. The partition correction moves into picking a proposal. The transitive-edge problem disappears, because a proposal states its own units and derives none. The viewer stays read-only.

Option A, a workflow in the target repository, is the only one that meets "on each PR creation and update". It adds a first .github/workflows/ file and needs a credential in CI. Do you accept that, or start with option C and add the workflow later?
