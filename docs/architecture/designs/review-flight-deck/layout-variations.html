The bind

A queue is not a set

The viewer reviews one pull request at a time. Previous, next, a strip of queue dots, four levels down the left rail. That shape is right for reading one change well, and it gives a reviewer nothing for the question they actually hold in their head with five pull requests open: do any of these fight each other, and should any of them be one review instead of two.

GitHub answers a narrower version of this with stacked pull requests. A stack is a parent-child chain the author declares in advance. The set a reviewer needs is assembled after the fact, by the reviewer, out of work several people opened without coordinating.

Outcome

A reviewer selects several pull requests, opens one surface that shows where they overlap, conflict, and reinforce each other, and leaves with a decision recorded against each one.

The browser never writes to GitHub. The surface records the call into the append-only ledger, and a terminal-side mode carries out the git work later, after an explicit confirmation.

The Claims Docket Rejected · coverage trap Frames: 3am on-call, regulator

One row per claim about the set, never per pull request. Each row carries the rule that produced it, the fields it read, and whether it could be computed at all. A claim the generator could not compute is printed as a row with its reason in place of the assertion, so a reviewer's blind spots sit on the record instead of being absent from it. A per-pull-request call is not typed. It falls out of the settled claims.

The Braid Chosen · epics E1 to E4 Frame: remove the load-bearing assumption

Delete the page. The unit of judgement stops being the pull request and becomes the region: a file and a line span more than one pull request writes. Five pull requests can collapse to nine stops, because a region only one pull request touches never becomes a stop. That is a real reduction in reviewer work rather than a rearrangement of it, and it is the only layout that sidesteps the browser entirely.

The Cut Chosen · epic E5, cold-start Frame: 100x, ten years

The reviewer never assembles a set. The queue arrives already partitioned into review units, each bracket labelled with the reason it exists and the precedent behind it. Correcting a wrong grouping is a cheaper judgement than building a right one, and an untouched bracket is itself a recorded decision. The precedent line under each bracket needs a decision history that does not exist yet. The partition itself does not. A cold-start proposer groups on conflict evidence with no precedent line, and the ranking arrives once the ledger has rows.

The verb set

What a developer actually gets to do

Every layout above records the same four calls. This is the part that changes a reviewer's day, and it is identical whichever surface wins.

Review alone

The one call a per-pull-request dock can never make honestly, because it cannot say what the pull request was judged against. Here the record names the set.

Combine

Name a base and the pull requests folded into it. Two changes that only make sense read together stop being two reviews.

Split

Name the pull request and the paths to cut along. A 324-file rename with a real fix buried in it becomes two reviews, one of which is trivial.

Order

Two pull requests that do not conflict but must land in sequence. Neither GitHub nor a stack expresses this for an unrelated pair.

The call is a record, not an action

The deck appends one line and stops. A terminal-side mode reads the ledger, shows the plan, and asks before it touches git. That keeps the browser out of GitHub, and it keeps the reviewer's reasoning attached to the thing it justified.

Challenge gate · settled

Three findings, and what was decided

Exploration surfaced these, and none of them were on the risk list. The chosen approach answered the first one by moving the computation rather than by restricting the surface.

1

The ledger cannot be written on two of three serving paths

The outcome says the surface records the call. That holds only under serve_bundle.py --allow-write. Under the documented python3 -m http.server the write returns 404. Under a published Artifact, ADR-0001's content policy blocks the request outright. Both fall back to browser storage with a message promising a sync that nothing implements, so a call made in a published deck never reaches the mode meant to act on it.

Settled: the finding dissolves. A terminal-side proposer writes through shared/ledger.py with direct file access, so no request is made and neither failure can happen. A published copy renders read-only and says so.

2

Two of your three evidence levels yield nothing today

Shared decisions and shared epics both join one pull request per key, so neither produces a single pair. Grouping epics by their design fixes it and produces real edges. Textual conflict needs both branch heads present, and this checkout has none of the open ones, so it needs a fetch step the design did not budget for.

Settled: deferred to the inflight-record-store design, which owns the pull-request entity gap. The cost is that textual conflict becomes the only strong signal, and it needs a branch fetch.

3

Your rejection of path overlap holds, for a sharper reason

You left shared-path overlap out. That is right, and not because it is cheap. It is the wrong resolution: 86 of 91 pairs share a prefix, and (root) alone is shared by 12 of 14 pull requests. Presence of overlap carries no information in this repo at any granularity. Only magnitude and specificity do. Twenty shared files under one design directory is a finding. One shared file is not.

Settled: the rejection stands. Regions come from real hunk headers, not from prefixes, so the chosen approach never needed the weak signal.

EpicOutcomeDepends on

E1 is the abort test, not a warm-up. If the stop list is not materially shorter than the shared-file list, the central claim of the approach is false and the design stops there for the cost of one script.

Provenance

How the options were found

Six isolated exploration frames with no shared transcript, then one separate critic pass that scored, clustered, and flagged traps. No frame saw another frame's output.

What is measured

Every count on this page comes from the committed bundle and the viewer source: field coverage, pair yield, join shapes, branch presence, ledger size, file lengths.

What is a prediction

Every claim about how a reviewer will behave, and every build-cost estimate. Nobody has used any of these five layouts.
