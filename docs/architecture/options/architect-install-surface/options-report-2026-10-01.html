This diagram answers one question: what must be present, and where, for a dispatch from a command file to reach the code that runs? The clay band marks the step where the call leaves the calling skill's own directory and leans on a prose fallback.

Steps 1 to 2

Resolution inside one plugin works

A command is a thin dispatcher into the skill of its own plugin. The vocabulary names this contract, and the seven command files are about 25 lines each.

Steps 3 to 4

The shared-skill call leans on prose

The skill prose first calls the skill by ID, and then states a manual fallback: read the file by path. Nothing mechanical checks that the ID resolves.

Result

The flow completes on a promise

Step 5 crosses a plugin boundary and depends on the manifest dependencies field, which guarantees co-installation. It grants no file path.

Directions and alternatives

Each direction shows the current shape, a proposed shape, the options, and my recommendation. ADR-0016, ADR-0017, and ADR-0025 ran their own option work on this surface. This page does not repeat their decisions. It tests the edges they left open. Every proposal below is a draft.

High

F1 · Do the cross-boundary skill IDs resolve, or does the prose fallback carry them?

Current
  1. The skill prose calls shared skills by ID: Skill("architect:ste-writing") at SKILL.md:200 and Skill("architect:mermaid") at SKILL.md:217.
  2. Neither skill ships under plugins/architect/skills/. Both live under shared/skills/, which install rewrites only as copied content.
  3. The same prose states a manual fallback for each call: if the call gives "Unknown skill", read the file by path. SKILL.md:282 also calls Skill("cobuilder-artifacts") into the sibling artifact plugin.

Effect: A call that fails costs a wasted agent turn, and a fallback read by path silently assumes the file is inside this plugin's own cache.

Proposed direction (draft)
  1. Write one test that scans the skill prose of each plugin.
  2. The test collects every Skill("X") ID the prose names.
  3. It asserts each ID maps to a shipped skill folder or a shared skill file under the calling plugin's own surface.
  4. It keeps the prose fallback as the escape hatch, but makes a new unresolvable ID fail the test suite, not a user's session.

Effect: The failure moves from a live session to a test run.

A A resolution test over skill proseOne test file. It walks skills/ and shared/skills/.LowNew. ADR-0016:276-279 already records this test pattern as the cheap follow-up for G1.
B Move shared skills into every plugin's real skills/ directoryCopy the two skills per plugin. Keep the symlinks.MediumDuplicates them. ADR-0017 chose vendoring instead.

Option A. Cheap check first: in one session, run the Skill("architect:ste-writing") call in a disposable session and record whether it resolves. That result alone decides whether the test asserts success or the fallback.

Medium

F2 · What guard exists when five co-installed plugins drift in version?

Current
  1. Any user can install or upgrade one plugin and not the others. ADR-0016 accepts four versions on one machine.
  2. The manifest dependencies field guarantees that a dependency plugin is installed. It carries no version floor.
  3. The shared bundle is the only contact surface, and shared/_bundle_meta.py:78 require_compatible() refuses a write against a newer bundle format.

Effect: A drifted install fails loudly, but only at write time, and only for code that calls the gate.

Proposed direction (draft)
  1. Keep the runtime gate. It is the contract ADR-0017 chose.
  2. Add one test: for each dependencies entry, assert the name resolves to a plugin the marketplace ships today.
  3. Do not try to pin cross-plugin version floors until the host documents support for them.

Effect: A typo or rename in a dependencies entry fails in tests, not in a user's install.

OptionWhat it needsCostStatus in the ADRs
A Keep the gate, add a dependencies-name testOne small test function.LowExtends tests/test_plugin_manifests.py:147.
B Version-floor pins in dependencies entriesHost support to be checked first.HighNothing records it today. Check the platform docs before any design.
C Keep today, no testNothing.LowThe current state.
Recommendation

Option A. Option B is real but blocked on a platform fact nobody checked. Record that check as the cheap first step.

Medium

T1 · Should the version of one plugin live in two fields?

Current
  1. Each plugin states a version in its plugin.json, and again in its marketplace.json entry.
  2. Three of five plugins hold two different numbers today: architect 0.6.0 versus 0.7.0, artifact 0.6.0 versus 0.6.2, implement 0.3.0 versus 0.3.1.
  3. No test compares the two fields for one plugin.

Effect: A release note or a changelog that reads one field and not the other reports the wrong version.

Proposed direction (draft)
  1. Decide which field is the source of truth.
  2. Add one test that reads both fields and fails on inequality.
  3. Update the stale field in the same commit as any bump.

Effect: The two fields can no longer drift silently.

Medium

T2 · Do one-job-one-install forces still hold for a 273-file plugin?

Current
  1. The architect plugin ships 273 tracked files, about 3.4 MB: 196 corpus cards and 41 book excerpts among them.
  2. ADR-0021 caps what a session reads from that corpus. It does not cap what the user installs.
  3. ADR-0016 rejected any split finer than one plugin per mode family, because a directory is not installable.

Effect: A user who wants only /architect:options carries the whole audit corpus and the debug engine.

Proposed direction (draft)
  1. Measure before deciding: what share of the install size is corpus rather than code.
  2. If the share is large, raise one gap for design mode: split-by-skill is not installable today, so a slim install needs a different unit.
  3. If it is small, record the force as solved and close the inquiry.

Effect: The judgment becomes a number. No redesign yet.

Medium

G1 · The name-collision invariant has no automated test

Current
  1. ADR-0016's addendum states the invariant: no plugin's own name may equal a skill folder or command basename it ships.
  2. The addendum ends by asking for a cheap test in tests/test_plugin_manifests.py.
  3. That file today covers manifests, agents, hooks, MCP, dependencies, and the shared symlink. It has no collision test.

Effect: A future rename can reintroduce the exact break the addendum reproduced, and no test run stops it.

Proposed direction (draft)
  1. Add one test: for each plugin, compare its manifest name against its skills/ folder names and commands/ basenames.
  2. Fail on equality.
  3. Cover F1's skill-ID check in the same test file while it is open.

Effect: The promised cheap fix lands. Two invariants get one home.

Low

G2 · Manifest repository URLs name the old repository

Current
  1. All five plugin.json files set repository to github.com/bjornslib/cobuilder-architect.
  2. The marketplace manifest names the real home: bjornslib/cobuilder-plugin.

Effect: A user who follows the manifest link lands on the pre-rename repository name.

Proposed direction (draft)
  1. Set the repository field of all five manifests to the repository the marketplace names.
  2. Or drop the field, if the platform fills it from the marketplace entry.

Effect: Links point at the repository a user actually looks at.
