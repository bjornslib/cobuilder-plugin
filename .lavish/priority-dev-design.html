The core idea

One pipeline, carried by one event log

Are we on the same page? Almost. Your chain is right, and it is cleaner than my v1 diagram. That diagram linked the interpreter straight to the actuator and to the queue, and it hid the policy inside the actuator.

Session→ Interpreter→ Events→ Policy→ Actuator→ Attention queue→ Notification queue
The event log sits under every stage. Each stage reads from its last cursor and appends events of its own.

Escalation is an action

The policy engine decides to escalate. The actuator carries it out by opening an item in the attention queue. A human answer comes back as an event, and the actuator sends it.

The advisor proposes, the policy decides

The advisor is a stage in the interpreter. It writes a proposed reply as an event. The policy engine is deterministic code, so the fixed deny list never depends on a model.

Event classProducerExamples
session.*Session adapterstarted, turn_ended, permission_requested, output, ended, liveness
fact.*Interpreter stagestatus, attention kind (skip, answer, decide, do), with confidence and an evidence reference
proposal.*Advisor stagea proposed reply or gate approval, with evidence

attention.*Attention queueopened, answered, expired
notification.*Notification queueplanned, delivered, failed

The part you changed most

The interpreter

The interpreter reads session.* events and emits fact.* and proposal.* events. Each stage declares what it reads and what it emits. A routing file sends an event to one stage or to several. Two stages that read the same events can run side by side, so the log holds both answers for a later comparison.

Stage typeWhat it doesReads transcript text
Fact mapperPlain code for structured facts only, such as a session that ended or a pane that stopped.No
System-1 classifierA fast model that answers typed questions about a transcript slice, such as the status, or whether a human must answer. Jev and a small language model are candidates.Yes
Advisor agentA model with tools. It reads the task record and the history, and writes a proposed reply. It runs only when the classifier says a reply is possible.Yes

Jev, as researched

  • A proprietary model from TypeSafe AI. Limited early access since 15 September 2026. Version listed: jev-1.13.0.
  • It answers typed questions: yes or no, a choice from a list, or a score. Each answer has a probability distribution and a confidence value. It writes no text and no reason.
  • The API limit is 64k tokens for each input.
  • TypeSafe claims 70 to 500 ms for each response and $0.042 for each million input tokens. The sources that I read show no independent benchmark.
  • Access is an HTTP API. You stated that Jev offers no self-hosting option. Data retention and rate limits are not stated. The classifier stage stays replaceable, so an open-weight model can take its place.

Fit. It matches the classifier stage, and the confidence value can drive the choice between acting and escalating.

Limits for us. No evidence quote, so another step must supply one. Early access may block use. A hosted API sends transcript text to a second vendor.

DSPy, from my own knowledge

  • A Python library for programs that call language models. A program declares typed signatures. Optimisers tune its prompts from labelled examples and a metric.
  • I did not re-check its current release in this session.

Fit. Shadow-mode records give labelled examples for the optimiser. This answers the lack of an evaluation target without setting one now.

Limits. A compiled program is a generated prompt. It must live in a reviewed file, and CLAUDE.md principle 2 says judgment lives in reference files. An ADR must settle this.

Unchecked. I expect a Jev call to fit as a custom module and not as a language-model backend, because its API takes typed questions and not a prompt.

Deployment

The service in Docker, the sessions on the host

The service holds the interpreter, the policy engine, the actuator, both queues, the inbox API, and the event log on a volume. A container cannot read a host tmux session by default, so the design needs a bridge.

OptionHow it worksRisk
Adapter host AcceptedA small process on the host runs the tmux adapter and talks to the service over HTTP. Hook scripts append events through it.One more process to install. It also suits a later cloud move, because an adapter can run wherever its sessions run.
MountsMount the tmux socket and the transcript folder into the container.It may fail on macOS, where Docker runs in a virtual machine. I have not tested this.
  • A desktop notification cannot come from inside a container. The desktop notifier is a host process that reads the notification stream.
  • The advisor agent needs model credentials inside the container. How to supply them is open.
  • Where tracker.py and bd run, in the container or on the host, is open.
