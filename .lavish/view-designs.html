What the lavish CLI does better, and what it lacks

Better: the anchor is computed at annotation time, from the live DOM

Its selector(el) walks up to five ancestors, short-circuits on a real id, and falls back to :nth-of-type. Text selections capture a real DOM range — node path plus character offset on both ends. So any element and any mid-sentence selection is annotatable with no prior authoring.

The earlier sketch wanted a data-fb attribute written into the page at build time. That forces the generator to decide in advance what is commentable, and it pollutes the markup. Strictly worse. Dropped.

Lacks: any durable record of what a person said

store.takeFeedback() returns the queued prompts and clears them in the same transaction. There is no per-comment id that survives a reload — uid is a WeakMap counter reset on every page load — no state, no thread, and no author field.

Verified on this machine: all 18 sessions in ~/.lavish-axi/state.json hold prompts: []. The only lifecycle state it ships anywhere is detected → queued → resolved, and that belongs to auto-detected layout warnings, not to anything a human wrote.

Cannot be adopted wholesale

Node ≥22, npx on every call, a background Express server on 127.0.0.1:4387, a blocking foreground poll as the notification path, and a dependency tree including Express, Excalidraw, Tailwind and Mermaid. Its share path uploads to a third-party host, which its own SKILL.md flags. Against an install surface of /plugin install and nothing else, that is disqualifying — the same test that rules out Postgres below.

Two more ideas worth taking

A queue-key dedupe. Re-annotating the same spot replaces the pending item instead of duplicating it. Cheap, and the sketch had nothing like it.

Machine findings stay in their own channel. The lavish CLI keeps layout warnings apart from human prompts. An automated finding must not compete with human intent in one inbox. The sketch collapsed the two.

Design C

The record model

The proposal was a small database. The need is real and already measured. The engine is the part to argue about.

Postgresout

A service

Fails the install-surface test that just disqualified the lavish CLI. /plugin install and nothing else means no daemon and no external service.

Local SQLitedeferred, not rejected

A file, not a service — but no reader yet

Stdlib in Python, zero install, real query semantics. It loses today on one fact: the viewer cannot read it. Six <script src> tags assign window globals, and export_artifact.py inlines each as literal JSON. Reaching SQLite needs WASM, which breaks the buildless viewer and the 16 MiB budget. So it would be a third layer with no reader.

JSONforced, not settled for

The primary consumer decides

data/index.json plus index.js, derived by a new build_index.py, full rebuild, never authored. The same rule build_adrs.py and build_designs.py already follow.

The engine is the reversible half. Identity is not.

What makes state referenceable is stable identity and resolvable joins, not the store that holds them. Get the ids right and a local SQLite file can be added later as a build-time index without touching a single authored record. Get the ids wrong and no engine helps.

The threshold that would earn it. A JSON index answers a lookup by id and a one-hop join by loading the file. It cannot answer an arbitrary traversal without loading everything — which ADRs govern the contexts touched by pull requests merged after a date. When a real question needs that, SQLite arrives as a build-time index beside index.json, not as a replacement for it.

We already have the database

story.json, adrs.json, designs.js, inventory.yaml and publish-manifest.json are tables in a file-based store with a schema_version, a migration ladder, and an authored-field guard. What is missing is not an engine. It is a declared entity model, stable identity across types, and an index that resolves the joins.

Where records live — and the one exception

The existing rule holds: authored source in docs/, derived projections in the bundle. index.json is derived and rebuilt in full.

A comment is the first record that is neither authored source nor derivable from it

A reader writes it at read time. It has no home in docs/, and no rebuild can reconstruct it. It gets an append-only store at <bundle-dir>/feedback/threads.ndjson, and the index reads it without owning it.

That asymmetry is worth naming rather than smoothing over. Comments join the paid art and the authored narrative as content a rebuild would destroy, which puts them under the same migration guard.

Four questions

  1. One index.json, or one file per entity type? One file is simpler. Several match the pattern already in data/.
  2. Does the index subsume adrs.js and designs.js, or sit beside them? build_index.py would be the sixth build script either way.
  3. Does the write endpoint land now, or does publishing become the default instead? A published page already carries comment threads with no new code. These two answers substitute for each other.
  4. Do comments join the migration guard from the first commit, or once a reader has written one worth losing?
