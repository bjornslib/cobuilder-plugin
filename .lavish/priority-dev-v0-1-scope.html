Should the event log be a queue such as RabbitMQ or Redis?

No. The log is the system of record. We must replay it to re-run Jev and the language model over history, to recover after a crash, and to audit what happened. A queue that deletes a message after delivery cannot do that. The storage section has the detail.

Should we start with Postgres, not SQLite?

Yes. You are right, and I change my recommendation. Docker is a given, the cloud is planned, and Postgres removes the mount risk that I raised for SQLite on Docker Desktop. The v0.1 lab has no service, so it uses plain files. Postgres arrives with the service in v0.2.

Attach to running sessions, or launch from priority.dev?

Attach to every running session by default, as you recommend. No one needs to launch sessions from priority.dev. Each session gets capabilities: read for all, send only inside tmux, and gate only where hooks are active.

Is the highest-risk assumption the right one?

Yes. It is whether we can turn a session into typed data and decide with confidence which cases an agent can answer alone. The next sections test it first, on your own history.

What could break the product

The riskiest assumption

We can read what a coding agent says in a session, turn it into typed data, and decide with high confidence which cases the agent can answer without the human and which cases must go to the human.

If this is false, the policy engine, the actuator, the queues, and the inbox have nothing reliable to act on. If it is true, the rest is engineering that we understand.

Assumption 1 comes first. It is the most uncertain, it carries the value, and it is the cheapest to test. A failed test still has a use. If we cannot trust auto-answers, the typed status and the priority ranking still cut interruptions, and the product ships as triage without auto-answer.

Your recommendation holds

Attaching to sessions

Attach to every running session by default. No one needs to launch a session from priority.dev.

Discovery

Any one of three signals is enough to read a session.

  • Watch ~/.claude/projects/*/*.jsonl for files that change.
  • List the tmux panes (tmux list-panes -a) and match the process tree to claude.
  • Optional hooks send the session id, the transcript path, and the working directory exactly.

Capabilities for each session

  • Read: every session.
  • Send: only inside tmux.
  • Gate: only where hooks are active.
  • A session in an editor terminal is read-only.
  • A session reads its hooks when it starts. I do not know whether a running session picks up new hooks. Install the hooks once, globally, and treat older sessions as read-only plus tmux send until they restart. Test this in v0.2 (my inference).
  • Without hooks, the match of a pane to a transcript file is a heuristic: the working directory and the latest change (my inference). claude agents --json can cross-check it (a preview feature).
  • Later, an optional priority start can launch a session inside tmux with a known name.
Your questions

Storage and queues

OptionFit
RabbitMQClassic queues remove a message when it is acknowledged. Streams (since 3.9) keep an append-only log. It adds a broker, and we still need a database for ranking and the ledger.
Redis StreamsAn append-only log with consumer groups. Persistence is a setting, and memory bounds it. We still need a second store.
Postgres RecommendedA table is the log. LISTEN/NOTIFY wakes readers. SKIP LOCKED gives a work queue. One store holds the log, the queues, and the ledger. The same engine runs in the cloud.

These statements come from my own knowledge, and I did not re-check them in this session. A broker can sit on top later as a transport, with the log as the source.

Two cautions with Postgres

  • Sequence values can become visible out of order when transactions overlap, so a reader at seq > cursor can skip a row. Let one process (the service) append, or use a gap-safe reader.
  • LISTEN/NOTIFY messages are not stored, and a payload has a limit of 8,000 bytes. Use them only to wake a reader, which then reads from its cursor.
Your ruling, with my reading

The action loop

You ruled that the actuator attempts an action and the policy accepts or rejects it. This is how I read it.

  1. The interpreter writes a proposal, such as a proposed reply.
  2. The actuator turns it into an attempt: an intent with an idempotency key. Nothing is sent.
  3. The policy engine accepts or rejects the attempt. The deny list is inside it. It writes a decision with the rule and the policy version.
  4. If it accepts, the actuator sends the input and records the effect. If it rejects, the actuator opens an attention item with the reason.
  5. Your answer becomes a new attempt. The policy accepts it by a rule for human answers.

This reading keeps one property: the policy decides before any send. A different reading, where the actuator sends first and the policy judges afterwards, cannot prevent harm. Please confirm the first reading (decision 1).
