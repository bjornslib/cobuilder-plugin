Stage 0 · Outcome

What this delivers

A developer runs up to 20 coding agents across several projects. Only the sessions that need a human reach the developer, ranked by the developer's own priorities. An advisor answers the rest under a policy that the developer sets and can audit.

Done when

  • The developer sees one ranked list of the items that wait for a human.
  • A session that needs no human never interrupts the developer.
  • Every automatic action has a ledger entry that names the policy rule and the evidence.
  • A high-priority item interrupts at once. A low-priority item waits for a batch.
  • The tmux adapter works first. A second adapter can replace it with no change to the interpreter or the actuator.

The problem today

The developer runs 4 or 5 agents. Each agent interrupts in the order of arrival. The interruption ignores the developer's priorities.

Many interruptions need no human, such as a routine permission or a question that the task record already answers. At 20 agents the developer cannot keep focus.

Not goals now

An evaluation target. A cloud host. Any dependency on herdr.

Decisions you made in the session

  • The name is priority.dev.
  • Three parts: adapters read events and send input, an interpreter decides what the events mean, an actuator takes actions.
  • tmux comes first. No part may depend on herdr.
  • Local first. A cloud host with resumable sessions comes later.
  • The advisor may approve gates and make decisions. You configure the allowed actions. Only insecure and destructive actions are off limits.
  • No evaluation target yet. Three things must be right: status from transcripts, respond versus escalate, and immediate versus batched delivery.

Contracts (predictions, not checks)

  • SessionEvent: session_id, cursor, ts, kind, ref. Kinds: session_started, prompt_submitted, tool_requested, permission_requested, turn_ended, notification, session_ended, liveness.
  • Command: kind, session_id, intent_id. Kinds: send_text, send_keys, answer_permission, interrupt, start, stop.
  • Verdict: session_id, cursor, policy_version, status, attention_kind (skip, answer, decide, do), question, evidence, confidence.
  • Decision: action (answer, escalate, wait), reply, rule_id, risk_tier, rationale.
  • Intent and Effect: written to the log before and after each command. The ledger joins them.

Stage 5 · The three parts to get right

Status, respond or escalate, and delivery

You named these three. Each has a design, an open point, and a way to learn the numbers that we do not have yet.

Status from transcripts

Layer one is plain code. It reduces hook events and pane liveness to a coarse status. Layer two runs only when a turn ends. The advisor reads the last turn and quotes the line that supports its status.

  • A session with no events for a set time while working becomes stuck. The time is not set. Shadow mode supplies it.
  • The advisor treats the transcript as untrusted data. A command in the transcript is text, never an instruction.

Respond or escalate

OutcomeMeaningWho acts
skipNo question and no action. The turn is information only.Nobody
answerThe task record, the policy, or an earlier decision answers it.The advisor, through the actuator
decideOnly the human has the choice, approval, or fact.The developer
doOnly the human can take the action, such as signing in.The developer

The actuator sends an answer only when all four checks pass.

  • The policy allows the action class.
  • The deny list passes.
  • The decision has the right shape.
  • The confidence meets the tier of the action.

In every other case the item escalates. A malformed reply escalates. The system never drops an item in silence. An escalation carries a recommended answer, the options, the evidence, and what happens if the developer does not answer.

Learning without an evaluation target. Shadow mode comes first. The advisor writes decisions and the actuator sends nothing. The log records what the developer did instead. The system also suggests a rule when the developer answers the same prompt the same way three times. The developer accepts or refuses it.

  • You set priority. The advisor may suggest a class and never sets one.
  • The order is project rank, then priority class, then age.
  • An item that waits past its limit moves up one class. It is never answered by default.
  • The inbox shows the wait time of each item, because a parked agent costs time.
  • No data supports the window lengths. They are starting values.
Stage 5 · Policy

What you configure and what stays fixed

You configure

  • Project rank and the priority class of each project.
  • Allowed action classes, each with a risk tier: low, look, or risky.
  • The confidence each tier needs before the advisor acts alone.
  • Delivery windows and the age limit for each class.
  • Rules that the system suggests from your repeated answers.

Fixed deny list (draft for your review)

Destructive. Deleting outside the project folder. Force push. Deleting a remote branch. Dropping a database. git reset --hard on unpushed work.

Insecure. Sending a secret to a network host. Writing a credential to a file or a log. Turning off a permission or sandbox check. Putting an API key in a worker environment. Running a downloaded script that no one reviewed.

The check runs in the actuator and, for hook events, at the hook. A hook event holds the tool input in a structured form, so the check does not parse a screen.
