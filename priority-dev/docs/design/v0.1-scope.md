## 1. The highest-risk assumption

Your guess is right. The assumption is this: **we can read what a coding agent says in a session, turn it into typed data, and decide with high confidence which cases the agent can answer without the human and which cases must go to the human.**

If this is false, the policy engine, the actuator, the queues, and the inbox have nothing reliable to act on. If it is true, the rest is engineering that we understand.

| Assumption | If it is wrong | How to test it | Version |
|---|---|---|---|
| 1. Interpretation: the cascade turns turn-end slices into typed data with few false auto-answers | The product has no value as designed | Offline, on past transcripts. No service. | v0.1 |
| 2. Attach: we can watch every running session live | The fleet view is incomplete | Live read-only run | v0.2 |
| 3. Send: tmux keystrokes reach a session reliably | An auto-answer cannot reach the agent | 100 send trials | v0.3 |
| 4. Trust: you accept auto-answers after a shadow review | Auto-answer stays off | Shadow data over weeks | v0.2 and v0.3 |
| 5. Capacity: the Pro plan sustains many sessions | Fewer than 20 sessions | One looping-task test, independent of our code | Any time |
| 6. Overlap: Claude Code auto mode already answers permission prompts | Our scope narrows to questions and ranking | Read the transcripts | v0.1 |

Assumption 1 comes first. It is the most uncertain, it carries the value, and it is the cheapest to test.

Even a failed test has a use. If we cannot trust auto-answers, the typed status and the priority ranking still cut interruptions. The product then ships as triage without auto-answer.

## 2. What the real transcripts show

I read the transcript of this session, which lives in this container. I counted record types and fields. I copied no content. The Claude Code version here is 2.1.309. Your Mac may differ.

- **Location and format.** `~/.claude/projects/<project folder>/<session id>.jsonl`, one JSON record for each line. This session has 1,099 records in 19.5 MB.
- **Record types.** `user`, `assistant`, `system`, `attachment`, `queue-operation`, `cost-state`, `mode`, `ai-title`, and others. Most are bookkeeping. The format is internal. The hooks docs say `transcript_path` may lag the live conversation (source: harness report). The parser must keep unknown fields and unknown record types.
- **Turn ends.** An `assistant` record whose `message.stop_reason` is `end_turn` marks a turn end. This session has 33. It has 221 records with `tool_use`.
- **Who comes next.** A `user` record has an `origin` field. After the 33 turn ends, the next input came from a human 5 times, from a peer subagent hand-back 12 times, and from a task notification 16 times. The field separates humans from automation.
- **Human replies here ran from 131 to 602 words.** This session is a design conversation. It is not typical of approval-heavy work. This container holds only this one session. The lab must therefore run on your own sessions on your Mac.
- **Permission decisions.** A `permissionDecision` field records the decision, its source, and its reason. Here: 72 by a classifier and 52 by a rule. Every source is `config`, because the session runs in auto mode. In sessions with hand approval I expect the source `user` (inferred).
- **Auto mode overlaps with our aim.** The 72 classifier decisions show that Claude Code already answers many permission prompts in auto mode. I do not know which plans have auto mode, or how reliable it is. This may narrow our scope toward questions and ranking. Section 3 includes a check.
- **Cost.** `cost-state` records hold the session cost and the usage for each model.

**What this gives us.** Past transcripts carry labels for free. After each turn end, the record shows what the human did: nothing, an approval, or new information.

## 3. The v0.1 lab

**Purpose.** Test assumption 1 on your own history, and learn what the typed schema must hold.

**In scope.**

1. A tolerant reader for the transcript files, and a segmenter that cuts a slice at each turn end. A slice is clipped to the input limit of Jev (64k tokens) and redacted.
2. The event schema, version 0 (Pydantic): transcript records, turn slices, and typed facts.
3. The cascade (DSPy): Jev first, the language model second, and a language-model-only baseline on a sample.
4. Labels from history, and a small terminal tool for labels by hand.
5. An evaluator and a report.

**Out of scope.** Docker, Postgres, a web server, tmux, hooks, the policy engine, the actuator, notifications, and any user interface.

**The typed questions (proposal).**

| Field | Type | Values |
|---|---|---|
| status | `Choice` | `done`, `waiting_answer`, `waiting_permission`, `blocked`, `failed`, `continuing` |
| needs_human | `Noul` | yes or no |
| answer_class | `Choice` | `none`, `approve_continue`, `pick_default`, `provide_fact`, `decide`, `external_action` |
| risk | `Score` | low, medium, high |
| priority_hint | `Score` | low, medium, high |

The language model also quotes the line that supports its reading. Jev gives no reason, so the quote comes from the second step.

**Labels.**

- **From history (free).** What followed the turn end: a human or automation, and for a human, the length and kind of the reply (an approval or continue, or new content). Ambiguous replies go to you.
- **By hand.** You label a sample with a small terminal tool: did a human need to answer, could an agent have answered, and which answer class. My proposal is 100 random slices plus every slice where the cascade and the history disagree. **Correction:** 150 slices cannot bound a rate of 1%. That needs about 299 slices with no errors, 473 with one, and 628 with two (inferred, not run). I estimate 30 seconds for each slice, so 2.5 to 4 hours for 300 to 500 slices. Start with 150 and extend if the bound needs it. See `components.md` section 5.
- **Permission prompts.** The `permissionDecision` source, where it exists.

**Metrics and go or no-go (proposed numbers, for you to change).**

| Metric | Meaning | Go if |
|---|---|---|
| False auto-answer rate (E1) | Of the cases the cascade would answer alone, the share where a human was needed | At most 1% |
| Interruption reduction | Of the cases where no human was needed, the share that the cascade does not forward | At least 50% |
| Status accuracy | The `status` field against the labels | At least 90% |
| needs_human recall | Of the cases that need a human, the share that the cascade flags | At least 95% |
| Forward rate, cost, latency | Share that goes to the language model, cost for each turn, 95th percentile latency | Reported, with no gate |
| Schema gaps | Slices that the typed schema could not express | Listed one by one |

The lab compares three setups: Jev only, the language model only, and the cascade. `ReAnchor` fits the thresholds on 70% of the labelled set, and the other 30% tests them. A sample of 100 cases cannot prove a rate of 1%. The report must show the confidence interval, and we may need more labels.

**If the lab fails.** If E1 stays above its limit at every threshold that gives 50% reduction, auto-answer is a no-go. The product continues as triage: typed status, ranking, and notifications.

**Stack.** Python 3.12, `uv`, Pydantic v2, DSPy pinned to a release that holds the decision types, Jev through `dspy.LM("typesafe:jev-latest")`, the language model through OpenRouter (`anthropic/claude-haiku-5.5`), plain files for events and labels, DuckDB or SQLite for the evaluation, a secret scanner such as `detect-secrets` for redaction, and a small terminal labelling tool.

**Where.** `priority-dev/` as its own project, with `pyproject.toml` and a `src` layout. The data stays on your Mac and Git ignores it.

**Privacy.** The lab reads your transcripts locally. The text that goes to Jev and to OpenRouter is redacted first. The first run uses 20 slices, so you can check the redaction before the full run. Three vendors see the text: TypeSafe, OpenRouter, and the model provider behind OpenRouter. TypeSafe does not state its retention. I have not checked the OpenRouter data policy.

**Effort.** I have not sized it. I will size it when we cut the slices.

## 5. Attaching to sessions

Your recommendation holds: **attach to every running session by default.** No one needs to launch a session from priority.dev.

- **Discovery.** Any one of three signals is enough to read a session. First, watch `~/.claude/projects/*/*.jsonl` for files that change. Second, list the tmux panes (`tmux list-panes -a`) and match the process tree to `claude`. Third, optional hooks send the session id, the transcript path, and the working directory exactly.
- **Capabilities for each session.** Read (all sessions), send (only in tmux), and gate (only where hooks are active).
- **Outside tmux.** A session in an editor terminal is read-only.
- **Hooks.** A session reads its hooks when it starts. I do not know whether a running session picks up new hooks. Install the hooks once, globally. Treat older sessions as read-only plus tmux send until they restart. Test this in v0.2 (inferred).
- **Without hooks**, the match of a pane to a transcript file is a heuristic: the working directory and the latest change (inferred). `claude agents --json` can cross-check (a preview feature).
- **Later.** An optional `priority start` can launch a session inside tmux with a known name.

## 6. Storage and queues

**Should the event log be a queue such as RabbitMQ or Redis?** No. The log is the system of record. We need to replay it, to re-run Jev and the language model over history and to recover after a crash. We need an audit trail. We need idempotent appends. A queue that deletes a message after delivery fails these needs.

| Option | Fit |
|---|---|
| RabbitMQ | Classic queues remove a message when it is acknowledged. Streams (since 3.9) keep an append-only log. It adds a broker, and we still need a database for ranking and the ledger. |
| Redis Streams | An append-only log with consumer groups. Persistence is a setting, and memory bounds it. We still need a second store. |
| Postgres | A table is the log. `LISTEN/NOTIFY` wakes readers. `SKIP LOCKED` gives a work queue. One store holds the log, the queues, and the ledger. The same engine runs in the cloud. |

(From my own knowledge, not re-checked in this session.) A broker can sit on top later as a transport, with the log as the source.

**Postgres first: you are right, and I change my recommendation.** Docker is a given, the cloud is planned, Postgres removes the mount question that I raised for SQLite on Docker Desktop, and it allows more than one writer. The cost is one more container. Two cautions:

1. Sequence values can become visible out of order when transactions overlap, so a reader at `seq > cursor` can skip a row. Let one process (the service) append, or use a gap-safe reader.
2. `LISTEN/NOTIFY` messages are not stored, and a payload has a limit of 8,000 bytes. Use them only to wake a reader, which then reads from its cursor.

The v0.1 lab has no service, so it uses plain files.

## 7. The action loop

Settled in round 4. The full text is in `components.md` section 2. In short:

1. The **interpreter** proposes. It is the only part that uses a model, and it has no power to send.
2. The **policy** decides. It is one pure function, `evaluate(action, state)`, with no model. It returns ALLOW, DENY, or ASK with a rule id, a policy hash, and the hash of the exact action.
3. The **actuator** executes. It is the only part with side effects. It checks the decision, runs `evaluate` again with fresh state, writes an intent, sends, and writes the effect. A DENY, an ASK, or a failed re-check opens an attention item.
4. Your answer is a human-authored proposal. A policy rule allows it, and it follows the same path.

## 8. The interpreter cascade

Jev answers typed questions at the end of each turn. A case goes to the language model when the confidence is below a threshold, or when the status is `waiting_answer`. The language model quotes its evidence and writes a typed proposal. The policy engine still decides.

- Jev: `dspy.LM("typesafe:jev-latest")` with `TYPESAFE_API_KEY`.
- Advisor: Haiku 5.5 through OpenRouter. DSPy reaches OpenRouter through LiteLLM (inferred). Check this in the first lab step.
- The confidence in DSPy is the distance from the threshold. It is not a calibrated probability.
